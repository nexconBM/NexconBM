# Nexcon Building Management website

Source for **https://nexconbm.com.au** — a static, bilingual (English / Traditional Chinese) marketing site for Nexcon Building Management, with a free serverless inspection-booking calendar.

- **Hosting:** GitHub Pages, serving the `main` branch directly (custom domain set by `CNAME`)
- **Stack:** plain HTML / CSS / JavaScript. No framework, no bundler. One small Python script (`build.py`) stitches a shared header and footer into every page.
- **Only backend:** a Google Apps Script "Web App" that reads/writes a Google Sheet, used by the booking feature. It is **not in this repo** (see [Booking system](#inspection-booking-system)).

## The build system (`build.py`)

There is exactly **one** copy of the header and footer (`partial/header.html`, `partial/footer.html`). `python build.py` writes them into every page listed in `PAGES`, replacing whatever sits between these marker comments:

```html
<!-- HEADER:START --> ...generated, don't edit by hand... <!-- HEADER:END -->
<!-- FOOTER:START --> ...generated, don't edit by hand... <!-- FOOTER:END -->
```

> **The rule that matters most:** page-specific `<script>` tags (`enquiry.js`, `case-studies.js`, `booking.js`, PapaParse, …) must go **after** `<!-- FOOTER:END -->`. Anything between the footer markers is silently deleted on the next build. This has caused real bugs — re-check it whenever you add a script tag.

### Template tokens

| Token | Becomes |
| --- | --- |
| `{{ROOT}}` | `""` on the homepage, `"../"` everywhere else (so relative links work at any depth) |
| `{{NAV_*_ACTIVE}}` | `class="is-active"` on the current page's nav link, empty elsewhere |
| `{{NAV_GROUP_BUILD_ACTIVE}}`, `{{NAV_GROUP_MGMT_ACTIVE}}` | ` is-active` on a dropdown button when the current page is in that group |

### Content-Security-Policy

Every page (including `404.html`) carries a `<meta http-equiv="Content-Security-Policy">` tag. It lives in one place, `partial/csp.html`, and `build.py` writes it into each `<head>` between `<!-- CSP:START -->` / `<!-- CSP:END -->` markers (inserted automatically after the viewport meta on first run).

The policy blocks **inline `<script>`** and only allows scripts from this site and `cdnjs.cloudflare.com`. Consequences for anyone editing the site:

- **Never add an inline `<script>` or `onclick=`-style handler.** The browser will silently refuse to run it. Put the code in a `.js` file (the old footer script now lives in `site.js` for this reason).
- **Adding a new third-party script, font host, image host, or `fetch()` target?** Add its origin to `partial/csp.html`, then run `python build.py`. Otherwise it will be blocked, with the reason shown in the browser console ("violates the following Content Security Policy directive").
- Inline `style=""` attributes are allowed (`style-src 'unsafe-inline'`), because they are used widely.
- Meta-tag CSP cannot set `frame-ancestors`; that would need real HTTP headers, which GitHub Pages doesn't offer.

### Adding a page

1. Create `new-page/index.html` containing bare `<!-- HEADER -->` and `<!-- FOOTER -->` placeholders.
2. Add it to `PAGES` in `build.py` (plus a `NAV_KEYS` entry and nav link in `partial/header.html` if it belongs in the menu).
3. Run `python build.py`.

## Testimonial on the home page

The "What our customers say" section (`#testimonials` in `index.html`, styled by `.testimonial*` in `styles.css`) holds one customer quote. Its words are the `home_testi_*` keys in `translations.js` (quote, name and suburb, service; English and Chinese). **Only publish a real customer's own words, with their permission** (fake or invented reviews are illegal under Australian consumer law). To add more, repeat the `<figure class="testimonial">` block with new keys. The part of the quote that is emphasised is wrapped in `<strong>` inside the translation text (the blockquote has `data-i18n-html` so the tag is kept); the highlight style is `.testimonial-quote strong`.

## Visitor analytics

`analytics.js` (loaded on every page from `partial/footer.html`) adds **Cloudflare Web Analytics**: free, no cookies, no profile of individual visitors. It counts page views, countries, browsers, referrers (where visitors came from) and page speed, and shows them in the Cloudflare dashboard under *Analytics & Logs → Web Analytics*.

- **Setup (done):** the site is added in Cloudflare (*Web Analytics*, hostname `nexconbm.com.au`) and its token is `TOKEN` in `analytics.js`. To switch to another Cloudflare site, replace `TOKEN` with the one from that site's snippet (the long string in `data-cf-beacon`). The token is **public** (it appears in the page source); it is not a secret like the Turnstile secret key. With the `PASTE_YOUR...` placeholder the file does nothing.
- **When it runs:** only on `nexconbm.com.au` / `www.` (so local previews and test copies are never counted), and not for visitors with Do Not Track or Global Privacy Control switched on. To leave your own visits out, run `localStorage.setItem("nexcon-no-analytics", "1")` once in the browser console on the live site (`removeItem` to undo).
- **Security policy:** `partial/csp.html` allows `https://static.cloudflareinsights.com` (script) and `https://cloudflareinsights.com` (reporting). The beacon can't be pinned with an integrity hash because Cloudflare updates it.
- **Privacy:** it uses no cookies, so no cookie banner is needed, but mention it in the privacy policy (see the guide's open items).

## Site search

A magnifier button opens a search box (`.search-toggle` buttons and `#searchPanel` in `partial/header.html`; on desktop the magnifier sits in the menu just before the language switcher, on phones and tablets a second copy sits beside the menu button, and CSS shows one at a time; styled by the `.search-*` rules in `styles.css`, driven by `search.js`, which `partial/footer.html` loads on every page). Nothing is sent anywhere: the search runs in the browser over one small JSON file per language that `build.py` writes on every run (`write_search_index`): `search-index-en.json`, `search-index-zh.json` (Traditional), `search-index-hans.json` (Simplified), about 25 KB each, in the site root. Each entry is a page's title, description and visible text (`<main>` only, so the menu and footer don't match everything), plus optional keywords.

- The visitor's language is the page's `<html lang>`, so a Chinese page searches the Chinese index.
- The **"Match all words"** tick box under the search field (`#searchAll`, ticked by default, remembered in this browser under `nexcon-search-all`) chooses how several words combine. Ticked: every typed word must be found on the page. Unticked: any one word is enough, and pages with more of the words rank higher. A title match ranks highest, then keywords, the description, and the body. If a multi-word search finds nothing while ticked, the message suggests unticking it. Chinese is matched as plain substrings (one character is enough; separate words with a space for the tick box to matter); Latin words need 2+ letters.
- **Adding a page** to `PAGES` adds it to the search automatically. To make a page findable by words that aren't in its text (for example "price" for the Inspections page, whose fees are drawn by script), add them to `SEARCH_EXTRA` in `build.py`, in English and Chinese.
- Words shown by the search come from the `search_*` keys in `translations.js` (both languages). Results are built with `textContent`, never `innerHTML`.
- Not searched: text that scripts add after load (the projects list from the Google Sheet, the booking calendar, fee results). Also left out on purpose, so results stay relevant (`SEARCH_SKIP_*` in `build.py`): the customer testimonial, anything inside a `<form>` (labels, dropdown options, tick boxes), hidden messages (anything with `hidden`, `data-nosnippet` or `display:none`, such as error, thank-you and loading text), and button-style links (`.pill`, `.text-link`) like "Start your project →". To keep another block out of the search, give it `data-nosnippet`.

## Bilingual support

English lives at `/page/`, Traditional Chinese at `/zh/page/`. The Chinese pages are **generated by `python build.py`** from the English pages plus `translations.js`, so Google can index them (the old toggle-only translation swapped text in the browser on the same URL, which search engines never saw).

- `translations.js` defines two flat objects, `en` and `zh`, as a plain JS object literal (comments allowed; it is **not** JSON, and `build.py` expects every value to be a double-quoted string).
- Elements with `data-i18n="some_key"` get their text replaced with that key's `zh` text in the `/zh/` copy (and again in the browser by `i18n.js`). Add `data-i18n-html` as well to set HTML instead.
- Each page's Chinese `<title>` and meta description are in `ZH_META` in `build.py`. A new page must get an entry there or the build stops.
- `build.py` also rewrites links in the `/zh/` copy (page links go to other `/zh/` pages, images/CSS/JS still load from the root), sets `lang="zh-Hant"`, the canonical URL and Open Graph tags, adds `hreflang` links to both language versions, and regenerates the sitemaps: `sitemap-en.xml` (English), `sitemap-zh.xml` (Simplified and Traditional Chinese) and `sitemap.xml`, the index listing both. Submit only `sitemap.xml` to Search Console.
- **Never edit files under `zh/` by hand.** Edit the English page or `translations.js`, then run `python build.py`.
- The toggle (`#langToggle`) links to the other language's URL (`data-alt-href`, filled in by the build). Only clicking it saves a choice (`localStorage` key `nexcon-lang-choice`); a visitor who chose Chinese and later opens an English URL is sent to its Chinese copy.
- Scripts that add text at runtime (booking widget, enquiry form, case studies, price calculator) read the language from `<html lang>` and use `t(key, fallback)`. Those keys still live in `translations.js`. If you ever script a search for unused keys, grep for `t("key"` in the `.js` files too, not just `data-i18n`.

**Adding a key:** add it to **both** `en` and `zh` with the same name, then reference it with `data-i18n` or `t()`. A key missing from `zh` stays in English on the Chinese page (the build prints a note naming it).

## Styling and cache-busting

All styling is in `styles.css`, using CSS custom properties for the palette (`--bordeaux`, `--mahogany`, `--sandstone`, …).

Pages reference assets with a version query string (`styles.css?v=42`, and `booking.js?v=21` on the building-inspections page). Browsers cache these aggressively, so a returning visitor can keep a stale copy indefinitely unless the number changes.

- **Edit `styles.css`** → bump `?v=` on **every** page that links it (all 12 live pages share one number and must be bumped together).
- **Edit `booking.js`** → bump its `?v=` in `building-inspections/index.html` (the only page that loads it).

Quick consistency check:

```bash
grep -rn "styles.css?v=" --include="*.html" .
```

### Fonts

All fonts are free Google Fonts, loaded by a `<link>` in every page's `<head>` (allowed by the CSP: `fonts.googleapis.com` for the stylesheet, `fonts.gstatic.com` for the files). The names are set once at the top of `styles.css`:

| Variable | Font | Used for | Weights loaded |
| --- | --- | --- | --- |
| `--ex` | **Archivo Expanded** | Headings, small uppercase labels (`.detail-label`, `.eyebrow`), the language buttons | 500, 600, 700, 800 |
| `--sans` | **Archivo** | Body text, menus, buttons, forms | 400, 500, 600, 700 |
| `--serif` | **Source Serif Pro** | The grey-pink lines under headings (`.lede`), the home hero line, footer tagline, `.quote`, and the testimonial (light italic) | 300 and 400, roman and italic |
| (fallback in all three) | **Noto Sans TC** / **Noto Sans SC** | Chinese text. `/zh/` pages use TC, `/zh-hans/` pages use SC (`html[lang="zh-Hans"]` in `styles.css` swaps the variables) | 400 to 800 |

- The Chinese font is large, so it is only loaded on Chinese pages: `build.py` (`CJK_FONT`) adds its `<link>` to the generated `/zh/` pages and swaps TC for SC on `/zh-hans/`, and `i18n.js` loads it as a fallback.
- **Only the weights above exist.** The serif has no bold face, so bold or 600+ serif text is a faked bold and looks rough. For emphasis in serif text use weight 400, colour or a highlight (as the testimonial does). Chinese text is the opposite: use bold (700) there.
- **To change a font:** change the name in the variable at the top of `styles.css` AND the `family=` list in the Google Fonts `<link>` of every page (it is written by hand in each page's head, not a shared partial, so search all `*.html` for `fonts.googleapis.com`; the generated `zh/` and `zh-hans/` copies follow the English pages after `python build.py`). Then bump the `styles.css?v=` number everywhere. A new font host also needs adding to `partial/csp.html`.

## Contact and enquiry forms

There are two enquiry forms: the main one on `/contact/` and a house-and-land one on `/house-and-land/`. Both are handled by `enquiry.js` (every `form[data-enquiry]`) and **post to the same Apps Script web app as the booking calendar**, as action `contact`. They used to go to a third-party form service whose address (including the business email) sat in the page source, so spammers could post straight to it and skip every check on the page. That service is gone from the site and from the CSP.

`enquiry.js`:

- joins ticked project-type checkboxes into one hidden field, and reveals a detail box for checkboxes with a matching `data-detail` id
- strips non-digits from phone fields as the visitor types
- tells the server which form it is with `data-enquiry-type="house_and_land"` (no attribute = `contact`)
- shows a thank-you, or a specific message when the server refuses (links, spam, too short, rate limit), in English and Chinese

> `enquiry.js` has its **own copy of `WEBAPP_URL`**, separate from `booking.js`. If the web app address ever changes, change it in **both** files, or one of the two features will silently break.

### Spam protection

The filters that matter live on the server, in `handleContact_` (`booking-apps-script.gs`), because anything in the browser can be skipped by calling the web app directly. The checks in `enquiry.js` only give real visitors a friendly message first.

- the hidden `website` box (parked off-screen, not `display:none`) must be empty; if it isn't, the request is silently dropped
- no web links (`http`, `www`, or a bare `something.com`), and a list of spam phrases (`SPAM_PATTERNS`: casino, promo code, giveaway, bitcoin, "click here", and so on). An ordinary dollar budget deliberately does not trip it
- message 5 to 2000 characters, valid email, phone with 1 to 15 digits (single spaces and one `+` at the very start are allowed, e.g. `+61 411 330 962`; nothing else), field lengths capped, only fields listed in `ENQUIRY_FORMS` are accepted
- rate limits: 3 per email address per hour, 20 per hour overall, 40 per day overall (`CONTACT_PER_*` constants)
- enquiries go to `CONTACT_EMAIL` with the visitor's address as reply-to, so Reply answers the customer

**The "Contacts" tab.** Every accepted enquiry (type `contact` or `house_and_land`, with its details and message) and every inspection booking (type `booking`, with its date, slot and address) is also written as one line on a tab called `Contacts` in the same Sheet (`logContact_`). It is created automatically, never trimmed, written as plain text, and is a searchable record of everyone who got in touch; for an enquiry it is a second copy of the email. **It is only a record.** The calendar and the 3-bookings limit read the `Bookings` tab alone, so a line on `Contacts` can never hold a time slot or block anyone. A failure while writing is swallowed so it can never change what the visitor sees. It holds customers' personal details, so keep the Sheet private.

**The "Blocked" tab.** Enquiries refused for a link, spam wording, the hidden trap box or the rate limit are listed (time, reason, form, name, email, phone, what they wrote) on a tab called `Blocked` in the same Google Sheet (`logBlocked_`). The tab is created automatically the first time something is blocked. Staff can skim it for a real customer caught by mistake. Robot-check failures, too-short messages and bad emails are not listed. It keeps the newest 300 lines (`BLOCKED_KEEP`), logs at most 30 an hour (`BLOCKED_PER_HOUR`), writes every cell as plain text, and a failure while logging is swallowed so it can never change what the visitor sees. It uses no email allowance. Blocked senders' contact details are stored there, so keep the Sheet private.

The house and land form has an optional **note box** (`name="message"`, labelled "Anything else we should know?"). It may be left empty; if something is typed it must be at least 5 characters, and it goes through the same link and spam checks as every message. The Contact form's message box is compulsory (it has `required`); `enquiry.js` reads that attribute to decide.

**Adding a field to a form:** add the input to the page, then add `[name, label, maxLength]` to that form's `fields` in `ENQUIRY_FORMS`, then redeploy the script. Unlisted fields are discarded. **Adding a new form:** add an entry to `ENQUIRY_FORMS` and set `data-enquiry-type` on the form.

### Daily email allowance

The web app sends mail as its Google account, which has a daily allowance (about 100 on a free Gmail account, about 1,500 on Google Workspace; a booking uses 2, an enquiry 1). The script protects against running out:

- When `EMAIL_WARN_AT` (20) or fewer sends remain, **one** warning email a day goes to `NOTIFY_EMAIL` (`warnIfLowOnEmail_`).
- When fewer than a request needs, plus `EMAIL_RESERVE` (6), remain, new bookings and enquiries are refused up front with `email_limit`, before anything is saved or any robot check is spent (`emailAllowanceOk_`). The site then says "try again tomorrow, or call us" (`contact_error_today`). The reserve keeps room for the warning itself.
- If a send fails anyway after a booking is saved, the customer is still told it's confirmed (the booking is in the Sheet). If an enquiry's one email fails, the visitor is told, because the visitor is told, and the enquiry is still kept on the `Contacts` tab with a note saying the email failed, so staff can follow up.
- To see today's remaining allowance, add a throwaway function that logs `MailApp.getRemainingDailyQuota()` and run it from the editor.

### Robot check (Cloudflare Turnstile)

Every booking and every enquiry also needs a Cloudflare Turnstile token (free, usually invisible to real visitors). `captcha.js` draws it and hands the token to `booking.js` / `enquiry.js`; the Apps Script sends the token to Cloudflare and refuses the request unless Cloudflare confirms it (`verifyCaptcha_`). Tokens work once, so the forms reset the check after every attempt.

- **Site key** (public): `SITE_KEY` at the top of `captcha.js`.
- **Secret key** (private): stored in the Apps Script under *Project Settings → Script properties* as `TURNSTILE_SECRET`. It is never in this repo and must never be pasted into one.
- **Fails closed:** if `TURNSTILE_SECRET` is missing, or Cloudflare can't be reached, every booking and enquiry is refused. A missing key can't silently switch the check off. After setting or changing the secret, run `checkSetup` once from the editor: Cloudflare should answer `success: false` with `invalid-input-response`, because the token it was sent is deliberately fake. `invalid-input-secret` means the stored secret is wrong.
- **Security policy:** `partial/csp.html` allows `https://challenges.cloudflare.com` for scripts and frames. The Cloudflare script can't be pinned with an integrity hash; Cloudflare changes it to stay ahead of robots.
- **Permissions:** the Apps Script needs the "connect to an external service" permission for this. Google asks once when you deploy.
- **Testing locally:** Cloudflare publishes dummy keys: site key `1x00000000000000000000AA` (always passes) with secret `1x0000000000000000000000000000000AA`. Never leave them in place on the live site.
- To switch to a different Cloudflare widget, change `SITE_KEY` and the `TURNSTILE_SECRET` property together.

A client-side daily limit (15/day, `localStorage` key `nexconEnquiries`) only guards against accidental repeat clicks and is not a real control.

## Case studies from a Google Sheet

The Projects page can render extra case studies from a published Google Sheet, so non-developers can add or edit them (English and/or Chinese) with no deploy.

- The sheet is published as CSV (File → Share → Publish to web → CSV); that URL is hardcoded as `SHEET_CSV_URL` in `case-studies.js`.
- On load, `case-studies.js` fetches and parses it (PapaParse, loaded from cdnjs on the Projects page only) and renders cards into `#sheet-projects`.

Row 1 headers (exact names):

```
title | title_zh | project | project_zh | location | location_zh | type | type_zh |
overview | overview_zh | features | features_zh | role | role_zh | challenges |
challenges_zh | result | result_zh | images | published
```

- A blank `_zh` cell falls back to the English text.
- `features` and `images` hold one item per line within a cell (Alt+Enter / Option+Return).
- `published` must be `TRUE` for a row to show.
- Google Drive image links are rewritten to embeddable form automatically; the Drive file must be shared "Anyone with the link".

Anyone with edit access to that sheet can change the live site instantly. The published CSV link itself is read-only.

## Inspection booking system

The building-inspections page has a month-view booking calendar. It costs nothing to run and needs no visitor login.

```
booking.js (this repo)  ──fetch──▶  Google Apps Script Web App  ──▶  Google Sheet ("Bookings" tab)
```

- **`booking.js`** renders the calendar and booking form and talks to the Web App. The Web App URL is hardcoded as `WEBAPP_URL`; it is public by design.
- **Apps Script** exposes `doGet` (list booked slots) and `doPost` (make a booking, or send an enquiry-form message), and sends the emails. It lives only in the Sheet's *Extensions → Apps Script* editor, **not in git**. A copy is saved as `booking-apps-script.gs` (see the [appendix](#appendix-apps-script-source)); the live editor is always the source of truth.
- **Sheet:** tab named exactly `Bookings`, header row `date | slot | name | email | phone | address | status | created`.

### Rules

Enforced client-side for a responsive UI **and** server-side in the Apps Script, so nothing relies on the browser:

- at least 3 business days' notice (weekends don't count: booking on a Friday, the earliest day is the following Wednesday)
- no more than 30 days ahead
- no Saturdays or Sundays
- no double-booking — the script takes `LockService.getScriptLock()` so check-then-write is atomic across simultaneous requests

Slots are `AM` (10:00 AM – 1:00 PM) and `PM` (2:00 PM – 5:00 PM).

"Today" comes from the server, not the visitor's device: `doGet` returns `today` (Melbourne date) and `booking.js` uses it for the calendar, falling back to the device clock only if the script hasn't been updated. Cancellations by email still need 24 hours' notice.

### Phone numbers

Phone boxes (booking and both enquiry forms) accept digits and single spaces, with one `+` allowed only as the first character: `0411 330 962`, `+61 411 330 962`. At least 1 and at most 15 digits (the international maximum); anything else is refused as `bad_phone`. The browser tidies the box as the visitor types (`enquiry.js`, `booking.js`), and the script checks again (`cleanPhone_` in `booking-apps-script.gs`). Stored as typed with repeated spaces tidied, in text-formatted cells. For the 3-bookings limit and the enquiry rate limit, spaces are ignored, so `0400 000 000` and `0400000000` are the same number (`phoneKey_`). The strict character set means a leading `+` can never be a spreadsheet formula.

### The payment notice

"The inspection report will be released upon receipt of full payment." (key `book_report_payment`, English and Chinese) is shown in large bold type (`.payment-notice`) at the top of the booking section on the Inspections page, in bold under every fee box (`.price-result-notice`, drawn by `pricing.js`, so the calculator and the booking form both show it), and in the customer's confirmation email. Change the wording in `translations.js` (both languages) and, for the email, in `handleBook_`.

### Property details and the fee

The booking form asks about the property (type, bedrooms, bathrooms, and tick boxes for a swimming pool and a Practical Completion Inspection) and shows the inspection fee live, using `pricing.js`. Pest control is a flat fee and hides the room fields. The answers are sent with the booking as `property_type`, `bedrooms`, `bathrooms`, `pci` and `pool`.

The script never trusts the page's price: `propertyFromRequest_` in `booking-apps-script.gs` checks the answers (known type, 1-6 bedrooms, 1-5 bathrooms, real booleans, pool only for houses, no PCI for pest control; anything else is refused as `bad_property`) and works the fee out again. The result goes into the staff email, the customer's confirmation email (as "Inspection fee: $650 + GST $65 = $715 total") and the `details` column of the booking's line on the `Contacts` tab. The `Bookings` tab keeps its 8 columns.

The answers are optional on the server, so a visitor still holding an older cached copy of the page can book (no fee lines are added). **The price table exists twice**: `pricing.js` (website) and `INSPECTION_PRICES` and friends at the top of `booking-apps-script.gs` (script). If the fee sheet changes, edit both, deploy a new script version, and bump the `?v=` on `pricing.js`. A test that compares the two tables on every combination of type, bedrooms, bathrooms, PCI and pool belongs in any change to either (the harness used during development did this; 542 combinations).

### Calendar behaviour

- Month grid, Monday-first. Disabled days: weekends, inside the 3-business-day window, or past 30 days.
- "Previous" stops at the current month; "Next" allows browsing exactly one month ahead.
- Picking a day shows its slots beneath the calendar; picking a slot opens the form (name, email, phone, property address).
- The widget never re-renders the whole calendar after a booking or conflict — that would wipe the success/warning message before it could be read. Each slot button has a stable id (`slot-YYYY-MM-DD-AM`) and only that button is swapped between open and taken. A background refetch keeps the data current.
- **3 active bookings per browser** is tracked in `localStorage` (`nexconMyBookings`). It is a courtesy limit only (clearing storage bypasses it). On each load the local list is reconciled against the live Sheet so staff-side cancellations free the slot.

### Cancellations are manual

A one-time "cancel" link in the confirmation email was tried and removed: some email apps (notably Outlook) open emailed links inside their own embedded frame, and Google's pages refuse to load inside a foreign frame, so the link failed for exactly the people who needed it.

Now: the on-page note and confirmation email tell customers to email `building@nexcongroup.com.au` at least 24 hours ahead. Staff open the Sheet and change that row's `status` from `booked` to `cancelled`; the slot is bookable again on the next page load.

### Google Sheets date gotcha

Sheets silently converts a `YYYY-MM-DD` string into a Date when a row is written, which breaks `===` comparisons on read-back (and broke double-booking detection). The script normalises every stored date through `normalizeDate_()` and forces the new date cell to plain text. Keep both if you edit the script.

### Setting it up from scratch

1. Create a Google Sheet with a `Bookings` tab and the header row above.
2. Paste the [appendix script](#appendix-apps-script-source) into *Extensions → Apps Script*.
3. *Deploy → New deployment → Web app*: Execute as **Me**, Who has access **Anyone**.
4. Put the resulting `/exec` URL in **both** `booking.js` and `enquiry.js` as `WEBAPP_URL`.

### Changing the Apps Script later

1. Edit in the Apps Script editor (there is no local copy to push).
2. *Deploy → Manage deployments →* edit the existing deployment *→ Version: New version → Deploy*. The URL stays the same, so `booking.js` needs no change.
3. Test: a plain GET of the URL should return `{"ok":true,"booked":[...]}`. Ideally make one real test booking, then clear it in the Sheet.

> When testing from the command line, use plain `curl -sL`. Apps Script answers with a 302; letting curl downgrade to GET on the redirect is correct. Forcing the method with `--post301/302/303` produces a misleading Google Drive "unable to open the file" page even though the first request already ran.

## Security notes

A code audit found no injection vulnerabilities.

**In good shape**

- No `eval`, `document.write`, or unescaped `innerHTML`. Every dynamic HTML write (booking widget, sheet-driven case studies, translations) goes through an `esc()` helper (a `textContent` round-trip) first.
- Case-study image URLs are restricted to `http`/`https` (blocks `javascript:`).
- No secrets, API keys, or credential files in the repo. The Apps Script URL being public is intentional.
- No `target="_blank"` links and no plain-`http://` resource loads.

**Hardening already done**

- A Content-Security-Policy on every page (see [above](#content-security-policy)): inline scripts and unknown script/connect hosts are blocked, limiting the damage if an XSS bug is ever introduced.
- PapaParse (cdnjs, Projects page) is pinned with an `integrity` (SRI) hash plus `crossorigin="anonymous"`, so a tampered copy is rejected. If you change the PapaParse version, update the hash too (cdnjs publishes it at `https://api.cdnjs.com/libraries/PapaParse/<version>?fields=sri`).

**Accepted limitations**

- The per-browser booking limit and the enquiry form's daily limit are client-side only.
- The robot check, link and spam-wording filters, length caps and rate limits (see [Spam protection](#spam-protection)) stop almost all automated abuse, but a determined human can still type a plausible message and tick the box. Bookings are protected by the booking rules plus a cap of 3 upcoming bookings per email address.

**Not fixable from this repository: HTTP security headers**

GitHub Pages cannot set response headers. Security scanners that only look at headers therefore report `X-Content-Type-Options`, `X-Frame-Options` and parts of `Content-Security-Policy` as missing, even though the real CSP is in a `<meta>` tag (which browsers do honour, except for `frame-ancestors`, which only works as a header). The practical risk is low (no logins; clickjacking would only trick someone into pressing a form button that still needs a robot check). To add real headers, put the domain behind Cloudflare (free plan; the nameservers are currently GoDaddy's) and add a *Modify Response Header* rule with `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and a `Content-Security-Policy` header that repeats `partial/csp.html` plus `frame-ancestors 'none'`. Import and check every existing DNS record (especially any mail records) before switching nameservers.

**Operational checks (not code)**

- The `Bookings` Sheet holds customer names, emails, phones and addresses — keep it shared only with the business's own Google account(s), never "anyone with the link".
- Confirm "Enforce HTTPS" is on under the repo's *Settings → Pages*.

## Deploying

There is no CI. GitHub Pages serves `main`; pushing is the deploy, and changes usually appear within a minute or two.

Before pushing:

- [ ] Edited `partial/header.html`, `partial/footer.html` or `partial/csp.html`? Run `python build.py`.
- [ ] Edited `styles.css`? Bump `?v=` on every page.
- [ ] Edited `booking.js`? Bump `?v=` in `building-inspections/index.html`.
- [ ] Added a page-specific `<script>`? It must be **after** `<!-- FOOTER:END -->`, and must be an external file (no inline scripts).
- [ ] Using a new external service or host? Add its origin to `partial/csp.html` and rebuild.
- [ ] Previewed locally (`python -m http.server 8000`).

`robots.txt` allows normal search engines and AI search/assistant crawlers (which fetch pages to answer a user's question) and disallows crawlers that collect content to train AI models.
